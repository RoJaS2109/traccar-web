Mensajes de Posición
Los equipos Rinho envían reportes de posición y eventos al servidor en diferentes formatos. Esta sección documenta la estructura de los mensajes y cómo configurarlos.

Los reportes pueden enviarse por GPRS, WiFi o SMS según la configuración del equipo y las reglas del motor de eventos.

Generación de Reportes
Los reportes se generan mediante el Comando G:


>Gttnnp<
Campo	Descripción
tt	Tipo de reporte (GP, CY, BP, etc.)
nn	Número de disparador (00-99)
p	Prioridad: H (alta), M (media), L (baja)
Ejemplo

>GGP00M<

Genera un reporte GP con disparador 00 y prioridad Media.

Reportes más Usados
GP - Reporte General de Posición

>GGP00M<

Contiene: ID, fecha/hora, posición, velocidad, rumbo, estado.

Formato de respuesta:


>RPGP00+2024082512345,-34.603722,-58.381592,120,270,3;ID=1234;*CC<

CY - Reporte Compacto
Menor tamaño de datos manteniendo información esencial.

BP - Reporte Binario
Máxima compresión para planes de datos limitados.

Prioridades
Prioridad	Código	Comportamiento
Alta	H	Envío inmediato, reintento continuo
Media	M	Envío en cola, reintento moderado
Baja	L	Almacenar si no hay conexión
Use prioridad Alta (H) solo para alertas críticas. El exceso de reportes de alta prioridad puede afectar la estabilidad de conexión.

Destinos de Envío
Destino	Código	Descripción
IP Principal	@IP0	Canal MAIN primario
IP Secundaria	@IP1	Canal MAIN secundario
IP WiFi	@IP3	Solo por WiFi
SMS	@SM0	Por mensaje de texto

Confirmación de Recepción (ACK)
Cuando el servidor recibe un reporte del equipo, debe responder con un ACK (acknowledge) para confirmar la recepción correcta.

📋 Formato del ACK

>ACK;#NNNN;ID=XXXX;*CC<
Campo	Descripción
ACK	Comando de confirmación
#NNNN	Número de mensaje del reporte recibido (hex)
ID=XXXX	ID del equipo
*CC	Checksum
💬 Ejemplo Completo
1. Equipo envía reporte

>RCY00020205000000-2778467-06425658000000-000090;DFFFFFF;IGN1;IN00;XP00;#0021;ID=1234;*59<

2. Servidor responde ACK

>ACK;#0021;ID=1234;*72<
El #0021 debe coincidir exactamente con el número de mensaje del reporte.

📱 ACK Simplificado (SMS)
Para responder desde un celular a un reporte SMS, se puede usar la versión corta:


>ACK;#0021<
Sin ID ni checksum, pero mantiene el número de mensaje.

⚠️ Comportamiento sin ACK
Si el equipo no recibe ACK:

Paso	Acción
1	Almacena el reporte en buffer (BlackBox)
2	Reintenta el envío
3	Después de varios intentos, cambia a IP secundaria
🔄 Comandos con Número de Mensaje
El servidor puede enviar comandos con número de mensaje (rango 0x8000 - 0xFFFF) para recibir confirmación del equipo.

Ejemplo
Servidor envía:


>SSSXP0011;#8001;ID=1234;*6A<

Equipo responde:


>RSSXP0011;#8001;ID=1234;*6B<

La respuesta con #8001 confirma que el comando fue ejecutado.

🔢 Rangos de Número de Mensaje
Rango	Origen	Uso
0x0000 - 0x7FFF	Equipo → Servidor	Reportes automáticos
0x8000 - 0xFFFF	Servidor → Equipo	Comandos con confirmación
🧮 Cálculo del Checksum
El checksum (*CC) se calcula realizando XOR de todos los caracteres desde > hasta * (sin incluir el *).

👉 Usa el Analizador de Checksums para calcular y verificar checksums.

Comando KA - Keep Alive Multi-Destino
Envía mensajes periódicos KA para mantener conexiones activas con servidores. Soporta servidor principal, backup o ambos simultáneamente.

Funciona automáticamente con WiFi y GPRS según la configuración de canales.

📋 Sintaxis
Configurar (SKA)

SKA[tiempo],[destino]

Parámetro	Descripción
tiempo	Intervalo en segundos (0-3600, 0=deshabilitar)
destino	B = Backup, M = Main, BM = Ambos (opcional, default: B)
Consultar (QKA)

QKA

Respuesta:


RKA[tiempo],[destino]

🎯 Destinos
Valor	Servidor	Descripción
B	Backup	Envía solo a servidor backup (default)
M	Main	Envía solo a servidor principal
BM	Ambos	Envía a ambos simultáneamente
💬 Ejemplos
Configurar Keep Alive

>SKA60,B<       // 1 min a BACK
>SKA120,M<      // 2 min a MAIN
>SKA180,BM<     // 3 min a ambos
>SKA60<         // 1 min a BACK (default)
>SKA0<          // Deshabilitar

Consultar configuración

>QKA<

Respuestas posibles:


>RKA60,B ...    // 60s a BACK
>RKA120,M ...   // 120s a MAIN
>RKA180,BM ...  // 180s a ambos

📌 Casos de Uso
Escenario	Comando	Intervalo
Alta disponibilidad	>SKA60,BM<	1 min a ambos
Solo principal	>SKA120,M<	2 min
Solo backup	>SKA30,B<	30 seg
Conexión crítica	>SKA10,BM<	10 seg a ambos
Ahorro de datos	>SKA600,M<	10 min
Deshabilitar	>SKA0<	-

Imprimibles

Enviar caracteres especiales a TRM

📦 Black Box (CXBB)
El módulo Black Box funciona como la “caja negra” de un avión: captura y almacena reportes antes y después de un evento, permitiendo analizar qué pasó en los momentos previos y posteriores a un incidente.

🤔 ¿Para qué sirve?
Imagina que ocurre un accidente o evento crítico. Con Black Box puedes:

🔙 Ver el pasado: Qué pasó en los segundos/minutos antes del evento
🔜 Ver el futuro: Qué pasó después del evento
📊 Análisis forense: Reconstruir exactamente qué ocurrió
🚗 Conducción: Analizar comportamiento del conductor ante frenadas bruscas
Analogía: Como el DVR de un auto que guarda los últimos minutos de video, Black Box guarda los últimos reportes de posición/estado del vehículo.

⚙️ Cómo funciona
Captura continua: El equipo graba reportes constantemente en segundo plano
Buffer circular: Mantiene las últimas N muestras (sobrescribe las más antiguas)
Evento/Disparo: Cuando ocurre el evento, “congela” el pasado y captura el futuro
Envío: Transmite todos los reportes (pasados + futuros) al servidor
🔧 Configuración
Comando SCXBB

>SCXBB,tipo,frecuencia,muestras_futuras,muestras_pasadas<

Parámetro	Descripción	Valores
tipo	Tipo de reporte a capturar	CQ, CP, MV, etc.
frecuencia	Intervalo entre capturas (× 1000ms)	1-255
muestras_futuras	Reportes a capturar después del evento	1-20
muestras_pasadas	Reportes del historial a incluir	1-20
Tipos de reporte recomendados
Tipo	Descripción	Uso típico
CQ	Posición compacta	Reconstrucción de ruta
MV	Movimiento	Análisis de conducción
CP	Completo	Diagnóstico detallado
🎯 Activación
Comando GBB - Disparar captura

>GBBnnP<

Parámetro	Descripción	Valores
nn	Número identificador	00-99
P	Prioridad de envío	L (baja), M (media), H (alta)
Ejemplo:


>GBB01H<    // Dispara Black Box con ID=01, prioridad alta

📋 Ejemplos prácticos
🚨 Análisis de accidente (alta frecuencia)
Capturar posición cada segundo, 10 segundos antes y 20 después:


>SCXBB,CQ,1,20,10<

Resultado: Al disparar, obtienes 30 reportes (10 pasados + 20 futuros) con resolución de 1 segundo.

🚗 Análisis de frenada brusca
Capturar movimiento cada 500ms, 15 muestras antes y después:


>SCXBB,MV,0.5,15,15<

Resultado: 30 reportes con resolución de medio segundo para analizar la maniobra.

📍 Monitoreo de ruta (baja frecuencia)
Capturar posición cada minuto, 5 antes y 20 después:


>SCXBB,CQ,60,20,5<

Resultado: 25 reportes cubriendo ~25 minutos de ruta.

🔗 Integración con Motor de Eventos
Puedes activar Black Box automáticamente ante eventos específicos:


// Activar Black Box ante frenada brusca
>SRL50E;TRG=ACC-;ACC={GBB01H}<

// Activar ante exceso de velocidad
>SRL51E;TRG=SPD+;ACC={GBB02H}<

// Activar ante desconexión de batería
>SRL52E;TRG=PWR-;ACC={GBB03H}<

Caso de uso real: Configura Black Box con GBB en las reglas de eventos críticos para tener siempre el contexto completo de qué pasó.

📊 Consulta
Comando QCXBB

>QCXBB<

Respuesta:


>RCXBB,CQ,1,20,10;ID=...

La precisión del modo Locator depende de la densidad de celdas del operador. En zonas urbanas puede ser de 200-500m, en zonas rurales de varios kilómetros.

Reporte B3
Reporte binario TAU compacto de 47 bytes que empaqueta la posición GPS, el estado del equipo y los datos de celda en una sola trama. Está pensado para reducir el volumen de datos transmitido: aproximadamente 70% menos que el reporte de texto equivalente.

Los reportes binarios TAU (B3 y B9) se asignan a eventos igual que los reportes de texto (tipo CQ / CY). El equipo los codifica y transmite directamente en binario.

¿Para qué sirve?
📉 Minimizar el consumo de datos móviles en flotas grandes
🛰️ Enlaces satelitales / LPWA donde cada byte cuenta
📍 Reporte de posición con estado de red y celda en una trama única
🔋 Transmisiones más cortas = menor consumo energético del módem
Asignación a eventos
El reporte se asigna a un evento con el código de dos letras B3, exactamente igual que los reportes de texto CQ o CY. Cuando el evento se dispara, el equipo genera la trama binaria de 47 bytes y la envía al destino configurado.

SMS no es un destino válido para reportes binarios. Si el destino asignado es SMS, la trama se descarta (el binario no se transmite por SMS). Use GPRS, Wi-Fi, backend o log.

Consulta por terminal (QBUS)
Al consultar el buffer por terminal con QBUS, la trama se muestra como hex dump con el prefijo RB3:.


>QBUS<
>RB3:3E52423368...<   // 47 bytes en hexadecimal

Estructura binaria (47 bytes)
Bytes	Campo	Descripción
0–3	Cabecera	ASCII >RB3
4–7	Fecha/hora	Epoch TAU (uint32, big-endian)
8	Evento	Código de evento que disparó el reporte
9–12	HDOP + longitud	HDOP (6 bits) + longitud TAU de 26 bits (lon × 10⁵ + 18000000)
13–16	Fix + satélites + latitud	Fix (2 bits) + satélites (4 bits) + latitud TAU de 25 bits (lat × 10⁵ + 9000000)
17	Edad de posición	Segundos desde el último fix válido (máx. 255)
18–19	Señal GSM + velocidad	CSQ (6 bits) + velocidad km/h (10 bits)
20–21	Registro de red + rumbo	Registro GSM/GPRS (3 + 3 bits) + rumbo en grados (9 bits)
22–23	Salidas + entradas	Salidas digitales XP (5 bits) + entradas IN (10 bits)
24–25	Alimentación + batería	Estado GPS/CEL + tensión de batería (12 bits)
26–29	Odómetro	Odómetro total (uint32, big-endian)
30	Batería backup	Nivel LiPo mapeado a 0–100%
31	Tecnología de red	-90 sin red, -91 2G, -92 3G, -93 4G LTE, -94 Cat-M1, -95 Cat-NB1
32–33	MCC	Mobile Country Code (uint16, big-endian)
34–35	MNC	Mobile Network Code (uint16, big-endian)
36–37	LAC	Location Area Code (uint16, big-endian)
38–39	Cell ID	Identificador de celda (uint16, big-endian)
40–43	ID equipo	Identificador del equipo (4 bytes)
44–45	Nº de mensaje	Contador de mensaje (uint16, big-endian)
46	Checksum	XOR de los bytes 0–45
Coordenadas: latitud y longitud se transmiten con offset TAU (lat × 10⁵ + 9000000, lon × 10⁵ + 18000000) para evitar el signo. El campo de tecnología de red usa valores negativos como identificador de RAT.

Reporte B9
Reporte binario TAU de 89 bytes que amplía al B3 con datos de acelerómetro (XYZ) y un trail de las últimas 10 posiciones GPS codificadas como deltas. Mantiene el mismo objetivo de eficiencia: aproximadamente 70% menos de datos que el reporte de texto equivalente.

Los reportes binarios TAU (B9 y B3) se asignan a eventos igual que los reportes de texto (tipo CQ / CY). El equipo los codifica y transmite directamente en binario.

¿Para qué sirve?
📈 Reportar la dinámica del vehículo (acelerómetro) junto a la posición
🧭 Enviar el recorrido reciente (10 posiciones) en una sola trama compacta
📉 Minimizar el consumo de datos móviles frente al reporte de texto
🛰️ Enlaces satelitales / LPWA con mayor densidad de información por byte
Asignación a eventos
El reporte se asigna a un evento con el código de dos letras B9, exactamente igual que los reportes de texto CQ o CY. Cuando el evento se dispara, el equipo genera la trama binaria de 89 bytes y la envía al destino configurado.

SMS no es un destino válido para reportes binarios. Si el destino asignado es SMS, la trama se descarta (el binario no se transmite por SMS). Use GPRS, Wi-Fi, backend o log.

Consulta por terminal (QBUS)
Al consultar el buffer por terminal con QBUS, la trama se muestra como hex dump con el prefijo RB9:.


>QBUS<
>RB9:3E52423968...<   // 89 bytes en hexadecimal

Estructura binaria (89 bytes)
Los bytes 0–23 comparten el mismo formato que el reporte B3 (cabecera, fecha/hora, posición, red). A partir del byte 24 se agregan acelerómetro y trail.

Bytes	Campo	Descripción
0–3	Cabecera	ASCII >RB9
4–7	Fecha/hora	Epoch TAU (uint32, big-endian)
8	Evento	Código de evento que disparó el reporte
9–12	HDOP + longitud	HDOP (6 bits) + longitud TAU de 26 bits (lon × 10⁵ + 18000000)
13–16	Fix + satélites + latitud	Fix (2 bits) + satélites (4 bits) + latitud TAU de 25 bits (lat × 10⁵ + 9000000)
17	Edad de posición	Segundos desde el último fix válido (máx. 255)
18–19	Señal GSM + velocidad	CSQ (6 bits) + velocidad km/h (10 bits)
20–21	Registro de red + rumbo	Registro GSM/GPRS (3 + 3 bits) + rumbo en grados (9 bits)
22–23	Salidas + entradas	Salidas digitales XP (5 bits) + entradas IN (10 bits)
24–29	Acelerómetro XYZ	Eje resultante + ejes Z / Y / X codificados con offset +999
30	Estado de movimiento	0 = detenido, 1 = en movimiento
31	Edad del dato	Antigüedad del trail
32–81	Trail de 10 posiciones	10 registros × 5 bytes: velocidad (8 bits) + rumbo (9 bits) + Δlat (11 bits) + Δlon (12 bits)
82–85	ID equipo	Identificador del equipo (4 bytes)
86–87	Nº de mensaje	Contador de mensaje (uint16, big-endian)
88	Checksum	XOR de los bytes 0–87
Acelerómetro (bytes 24–29)
Se transmite el eje resultante junto a los tres ejes codificados con un offset de +999: el eje X directo, el eje Y dividido por 32 y el eje Z dividido por 4. El byte 30 indica si el vehículo está detenido o en movimiento.

Trail de posiciones (bytes 32–81)
Cada uno de los 10 registros (5 bytes) guarda una posición del recorrido reciente como delta respecto a la posición del evento:

Δlat: (Δlat / 2) + 999 en 11 bits (Δ en grados × 10⁵)
Δlon: (Δlon / 16) + 999 en 12 bits (Δ en grados × 10⁵)
Junto con velocidad (8 bits) y rumbo (9 bits)
Un registro cuyo primer byte es 255 indica una posición inválida / vacía (menos de 10 puntos disponibles).

📋 Sintaxis

EVAL expresión[:formato[:valor_error]]

Parámetro	Descripción	Default
expresión	Operación o consulta a evaluar	(obligatorio)
formato	Formato de salida estilo printf	%.2f
valor_error	Valor si falla la evaluación	ERR
Dentro de la expresión, los argumentos de funciones con múltiples parámetros se separan con ; (punto y coma), no con coma. Ejemplo: ECU(0;0), MBS(1;2). La expresión finaliza con el separador de formato : o con el cierre del mensaje del protocolo (<).

💬 Ejemplos Prácticos
Rumbo GPS (HDG)

>EVAL HDG<
Retorna rumbo actual en grados (0-360°). Ejemplo: 185.00


>EVAL HDG ge 180<
Retorna 1.00 si el vehículo apunta hacia el sur-oeste-norte (180°-360°).


>EVAL (HDG ge 0) && (HDG lt 90)<
Retorna 1.00 si apunta hacia el norte-este (0°-90°).

Suma de parámetros ECU

>EVAL ECU(0;0) + ECU(1;0) + ECU(2;0):%0.2f<
Suma valores ECU de los índices 0, 1 y 2.

Comparación AIN

>EVAL AIN(0) gt 500<
Retorna 1.00 si AIN(0) > 500, sino 0.00.

Lógica compuesta

>EVAL (V gt 150) && (AIN(0) lt 100)<
Verifica condición compuesta sobre voltaje y entrada analógica.

Cálculo con formato

>EVAL (10 * 5) + 3:%0.3f<
Resultado: 53.000

Expresión compleja

>EVAL ((AIN(0) * 10) + (AIN(1) * 5)) / 2:%0.2f:NA<
Calcula promedio ponderado con formato personalizado y error NA.

Máscara bitwise

>EVAL IN(0) & 0x0F:%X<
Aplica máscara a entrada digital y muestra en hexadecimal.

Shift bits

>EVAL 8 sr 2<
Resultado: 2.00 (8 >> 2)

División con formato entero

>EVAL 25 / 4:%d<
Resultado: 6 (división entera)

Conversión de temperatura

>EVAL (AIN(0) * 0.1) - 40:%0.1f:ERR<
Convierte lectura ADC a temperatura con error ERR.

Error	Causa	Solución
ERR	Variable no definida o sintaxis incorrecta	Verifica ortografía, usa valor_error
Inf	División por cero	Valida divisor o usa valor_error
Sintaxis	Paréntesis desbalanceados	Revisa estructura de expresión
Índice	Fuera de rango (ej: AIN(9))	Consulta rangos válidos del modelo

Interpretación de campos
Entradas digitales (II)
El byte II contiene el estado de IGN y las entradas IN en formato hexadecimal:

Bit	7 (MSB)	6	5	4	3	2	1	0 (LSB)
Señal	IGN	IN6	IN5	IN4	IN3	IN2	IN1	IN0
Ejemplo: II = 81 (hex) = 10000001 (bin) → IGN=1, IN0=1, resto=0

Coordenadas
Latitud: Formato ±DDMMMMM (grados + minutos×1000)
Longitud: Formato ±DDDMMMMM (grados + minutos×1000)
Signo + = Norte/Este, Signo - = Sur/Oeste

Comportamiento sin GPS
Ante la carencia de señal GPS, los campos de fecha (AAAAAA) y hora (BBBBBB) tomarán el valor del momento de generación del mensaje desde el reloj de tiempo real (RTC), en lugar de los datos de posición GPS.

Número de mensaje (LLLL)
Este campo se añade únicamente a los mensajes GP que se descargan del buffer de reportes del equipo. Permite identificar el orden de los reportes en la cola.


Reportes Extendidos
Los reportes extendidos incluyen información adicional al reporte básico GP/CY: datos de GPS, GSM, batería, temperatura, horómetro, CAN, etc.
